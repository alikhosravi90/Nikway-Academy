# Read-only Moodle frontend bridge

Run `python3 scripts/moodle-webservice-setup.py` on the local installation host. This enables REST and creates a restricted external service with only `core_webservice_get_site_info`, `core_enrol_get_users_courses`, and `core_course_get_contents`. Two prebound OIDC subjects receive individual seven-day tokens and a role granting only `webservice/rest:use`; their existing course roles are preserved. Provisioning validates provider binding first and refuses service function/profile drift. The private output `infra/moodle/runtime/webservice-tokens.json` must remain ignored, mode0600 and mounted read-only into the API. Never put it in frontend environment variables or Git.

Set API `MOODLE_TOKENS_FILE` to that mount, `MOODLE_REST_URL=http://moodle/webservice/rest/server.php`, `MOODLE_URL=http://localhost:18701`, and `MOODLE_TENANT_ID` to the explicitly allowed tenant. The API must reach Moodle on an isolated Docker network using alias `moodle`. Host execution uses the localhost18701 REST endpoint. Redirects are refused; timeout is five seconds and response size two MB. HTTP transport is trusted-local-pilot scope only.

`GET /api/integrations/moodle/overview` uses the existing authenticated active membership Context. It accepts no identity/course selection from the browser. Tenant mismatch returns disabled; unknown subject403; mismatched remote username/userid, unavailable/expired service503. It reads that user's own enrolments and projects only course/module names, safe local URLs and completion state. Tokens, raw content, site information and other user data never enter the response.

Response: `{enabled:true,source:"moodle",url,progress_sync:false,courses:[{id,title,url,progress,modules:[{id,title,type,url,completion}]}]}`. `progress` and `completion` can be null. Progress100 means tracked activity completion, not passing the assessment. This endpoint provides a read-through view, not database synchronization. Existing Academy membership checks still apply to every request; already-open Moodle sessions have their existing separate lifetime.

Tokens expire after seven days. Setup refuses expired existing tokens; rotation/revocation is an explicit Moodle administrator action, followed by setup to refresh the private file. Disabling this dedicated external service revokes bridge access without disabling accounts or changing learning records. The pilot does not claim production-ready HTTPS/JWT hardening.

Runtime limits: ten courses and one thousand modules per response, ten-second elapsed request budget checked before/after each upstream call, each socket timeout capped at five seconds and remaining budget. This is not a hard wall-clock cancellation of a slow-trickling HTTP response; upstream work is synchronous and holds the existing authenticated DB context. The local pilot has one course. Runtime identity validates Moodle userid/username; `auth` and `idnumber` provider binding are verified during provisioning, not on every REST call. Moodle suspension/deletion is enforced by its web-service authentication. Administrative provider-binding drift requires reprovisioning review or token revocation. Existing service role capabilities are checked fail-closed before assignments.
